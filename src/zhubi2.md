# 竹篦二号 (Zhubi v2) — QQ群Bot Idle游戏设计文档

## 一、架构分析

### 1.1 实现难度

| 维度 | 评估 | 说明 |
|------|------|------|
| 核心状态机 | 中 | 玩家→材料→配方→机器→计划，五层状态管理，需要ACID事务保证材料不重复消耗 |
| 自动化引擎 | 中高 | 定时tick计算所有活跃计划产出，需处理循环配方、材料竞争、产出回退 |
| 配方图 | 中 | 材料→物品 DAG，需要闭环检测(防止循环合成)，路径查找(从材料到目标的合成链) |
| Web UI | 高 | 额外技术栈，需内网穿透/端口映射，OAuth或token鉴权，与bot状态同步 |
| 合并转发 | 低 | OneBot协议原生支持，节点消息构造即可 |
| 持久化 | 低 | SQLite单文件足够，玩家量级不过千 |

**总体**: 核心bot部分中等难度，Web UI显著抬高成本。建议**先做bot纯文本交互验证核心循环，Web UI作为二期**。

### 1.2 性能要求

- **计算模型**: 非实时tick，采用"玩家查询时结算"的懒计算模式
- 每个玩家最多几十台机器、几十条计划，结算复杂度 O(机器数 × 计划数) ≈ 数百次运算/查询
- SQLite单表百人规模，查询<10ms
- 内存占用<100MB
- **结论**: 性能不构成瓶颈，树莓派级别设备即可承载

### 1.3 Bot交互频繁程度

- 限速: 每8小时N次操作(建议N=10-20)
- 单用户日均操作上限: 30-60次(3个8小时窗口)
- 假设群内20个活跃玩家，日均请求<1200条
- QQ协议无压力
- **结论**: 交互频率极低，不存在刷屏问题

### 1.4 是否容易刷屏

- 每条指令一条回复，不主动推送
- `/i`查询可能产出较长信息(材料列表+机器状态+计划列表)，可通过合并转发打包为一条
- 自动化结算不额外发消息，只在玩家查询时呈现
- **结论**: 不会刷屏。最差情况下一条合并转发消息承载全部内容

### 1.5 扩展性

- 指令系统: 新增指令只需注册handler
- 材料/配方/机器: 数据驱动，JSON/YAML配置
- 阶段解锁: 里程碑表控制gating逻辑
- 计划类型: 策略模式，新增计划模板不改核心引擎
- **结论**: 架构扩展性好，核心是CRUD+状态机，天然适合迭代

### 1.6 可行性总结

**可行**。核心bot+idle引擎可在单人2-4周完成MVP。Web UI增加2-4周。建议分两期交付。

## 二、核心指令设计

### 2.1 指令总览

| 指令 | 名称 | 功能 | 限速消耗 |
|------|------|------|----------|
| `/d` | dig | 采集随机材料 | 1次 |
| `/c` | craft | 合成工具/物品/机器 | 1次 |
| `/b` | build | 放置/部署机器或物品 | 1次 |
| `/p` | plan | 定义机器自动化计划 | 1次 |
| `/i` | idle_check | 查询状态/配方/需求 | 0次(查询免费) |

### 2.2 `/d` — 挖掘

```
/d [次数]
```

- 次数默认1，最大5(单次调用消耗等量操作额度)
- 随机获取材料池中的若干材料
- **材料数量**: 基础值 + 已放置增量内容加成(如放置的采集机器等级)
- **材料等级**: 当前解锁的最高里程碑决定材料池范围
- 里程碑例: 制作LV马达 → 解锁LV材料挖掘；制作MV马达 → 解锁MV材料挖掘
- 返回格式: 获得材料清单(合并转发)

### 2.3 `/c` — 合成

```
/c <目标物品名> [数量]
/c list [关键词]     — 查询可合成列表
/c recipe <物品名>   — 查询配方需求
```

- 消耗背包材料→产出物品
- 合成需满足:
  1. 配方已解锁(通过里程碑或前置合成)
  2. 材料数量足够
  3. 所需合成站已放置(如工作台→基础合成，组装机→电路合成)
- 合成产物分三类: **工具**(手持消耗品)、**物品**(中间材料)、**机器**(可放置)
- 返回格式: 消耗清单→获得产物(合并转发)

### 2.4 `/b` — 放置

```
/b <物品名> [数量]
/b list               — 查看已放置内容
```

- 将机器或特定物品从背包放置到"基地"
- 放置后机器可被`/p`引用
- 放置后物品(如祭坛、图腾)产生被动增益
- 放置消耗操作额度，但不消耗材料(材料已在合成时消耗)
- 返回格式: 放置结果 + 当前基地布局摘要

### 2.5 `/p` — 计划

```
/p <机器名> <配方名> [参数...]
参数:
  --priority <1-99>   优先级，数字越小越优先
  --pct <1-100>       投入材料百分比
  --limit <N>         产出达到N后自动停止
  --continuous        持续执行(默认模式，材料够就做)
/p list               查看当前所有计划
/p cancel <计划ID>    取消计划
```

- 指定某台已放置机器执行特定配方
- 机器可有多个计划(不同配方)，按优先级竞争材料
- 多条计划需要同种材料时: 优先级高的先分配，同级按创建时间
- `--limit`模式: 达到目标产量后计划自动暂停，材料释放给其他计划
- `--pct`模式: 只投入库存材料的指定百分比，保留部分给其他计划
- `--continuous`: 只要有足够材料就生产，无上限(默认)
- 自动化结算: 玩家查询时懒计算，或每小时批量tick
- 返回格式: 计划确认 + 预计产出时间(基于当前材料存量估算)

### 2.6 `/i` — 查询

```
/i                   — 我的状态摘要
/i inv               — 材料库存
/i base              — 基地布局
/i plans             — 活跃计划
/i recipe <物品名>   — 查询配方(同/c recipe)
/i milestone         — 里程碑进度
/i all               — 全部信息(合并转发打包)
```

- 查询不消耗操作额度
- `/i all`为合并转发消息，包含所有子项
- 可附带`@用户`查询他人公开信息(如/i inv @某人)

## 三、Idle循环设计

### 3.1 核心循环

```
挖掘(/d) → 材料积累 → 合成(/c)工具/机器 → 放置(/b)机器
    ↑                                                    ↓
    └── 自动采集产出 ←── 计划(/p)定义自动化 ←── 机器就绪
```

### 3.2 双轨进度

| 轨道 | 驱动方式 | 解锁内容 |
|------|----------|----------|
| **里程碑轨** | 合成特定物品(如LV马达) | 解锁新材料挖掘、新配方 |
| **增量轨** | 放置机器数量/等级 | 提高采集量、合成速度、自动化效率 |

### 3.3 离线结算

- 玩家离线期间，活跃计划继续执行
- 结算时机: 玩家下次发送任意指令(/d /c /p /i等)时触发离线结算
- 离线时长上限: 24小时(防止新玩家回归时结算量爆炸)
- 结算逻辑:
  1. 计算离线时长 T
  2. 遍历所有活跃计划，按优先级分配材料
  3. 每轮分配后更新库存，迭代直到材料不足以执行任何计划
  4. 产出写入库存，消耗从库存扣除
  5. 生成离线收益摘要(合并转发)
- 离线结算不消耗操作额度

### 3.4 转生(Prestige)系统设计

**触发条件**: 达成当前阶段全部里程碑 + 积累一定量"终极产物"

**转生效果**:
- 清空: 材料、工具、机器、计划全部重置
- 保留: 转生点数(Tokens)、已解锁配方记录、成就
- 增益: 转生点数可兑换永久加成(采集量+%、合成速度×、自动化效率×)

**多层转生**(GTNH电压对应):

| 转生层 | 命名 | 解锁条件 | Token增益 |
|--------|------|----------|-----------|
| 1层 | 蒸汽转生 | 完成蒸汽时代全部里程碑 | +10%采集量 |
| 2层 | LV转生 | 完成LV时代全部里程碑 | +25%采集量, +10%合成速度 |
| 3层 | MV转生 | 完成MV时代全部里程碑 | +50%采集量, +25%合成速度, 自动化×1.5 |
| ... | ... | ... | ... |

**转生收益公式**:
```
Token获得量 = floor(当前阶段总产出价值 / 阶段基准值) × (1 + 0.1 × 转生次数)
```

## 四、GTNH风格阶段划分

### 4.1 阶段总览

借鉴GTNH电压层级设计，每个阶段有硬性卡脖子节点：

| 阶段 | 代号 | 卡脖子节点 | 解锁能力 |
|------|------|------------|----------|
| 0 | 石器时代 | 建造第一台工作台 | 基础合成 |
| 1 | 蒸汽时代 | 制造蒸汽引擎 | 基础自动化(/p可用) |
| 2 | LV | 制造LV马达 | LV材料可挖掘 |
| 3 | MV | 制造MV电解器 | 材料分解、化工合成 |
| 4 | HV | 制造HV洁净室 | 高级电路、芯片合成 |
| 5 | EV | 制造EV核反应堆 | 大量能源、高级矿机 |
| 6 | IV | 制造IV组装线 | 大规模并行合成 |
| 7+ | LuV~MAX | 层层递进 | 转生层逐步解锁 |

### 4.2 阶段0: 石器时代

```
入口状态: 无任何工具
卡脖子节点: 用/d采集基础材料(木头、石头、粘土) → /c合成工作台 → /b放置工作台
解锁:
  - 工作台放置后可合成基础工具(石斧、石镐)
  - /d采集量提升2倍
时间预估: 2-3个操作周期(16-24小时)
```

### 4.3 阶段1: 蒸汽时代

```
入口状态: 有工作台
卡脖子节点: 采集铜/锡/铁矿石 → 合成蒸汽引擎 → 放置蒸汽引擎
解锁:
  - 蒸汽引擎放置后解锁/p指令
  - 可创建第一条自动化计划(自动烧炼)
  - 合成配方解锁: 基础机器框架
时间预估: 5-8个操作周期
```

### 4.4 阶段2: LV (Low Voltage)

```
入口状态: 蒸汽引擎已放置
卡脖子节点: 制造LV马达(需: 精炼铁板×4 + 铜线×8 + 基础电路×2)
  - 基础电路需: 工作台 + 铜板 + 树脂(新采集材料)
  - LV马达是第一个跨越多步合成的硬骨头
解锁:
  - /d可采集LV级材料(铝、镍、铬)
  - 解锁电力机器(组装机、线材机、弯曲机)
  - 自动化可跨机器串联(机器A产出→机器B消耗)
时间预估: 15-20个操作周期
```

### 4.5 阶段3: MV (Medium Voltage)

```
入口状态: LV马达已制造
卡脖子节点: 制造MV电解器(需: 不锈钢外壳×2 + LV马达×2 + MV电路×4)
  - MV电路需: 镓砷晶体(EBF熔炼) → 二极管
  - 不锈钢需: 铬+锰+铁(铬是LV解锁的新矿物)
解锁:
  - 材料分解(/c可拆分化合物)
  - 化工合成配方线
  - 解锁魔法线(Thaumcraft式研究)
时间预估: 30-40个操作周期
```

### 4.6 阶段4+: HV及以上

```
HV卡脖子: 洁净室(需IV级净化组件 + 大量不锈钢)
  解锁: 高级电路、芯片合成、大规模化工
EV卡脖子: 核反应堆(需HV级组件 + 铀 + 高级合金)
  解锁: 大量能源、高级矿机(采集量飞跃)
IV卡脖子: 组装线(需EV级精密组件 + 超级电容)
  解锁: 并行合成(单次/c可合成多件)、转生系统解锁
LuV+: 转生后世界，保留token增益重新推进，每次更快
```

### 4.7 卡脖子节点设计原则

1. **多步依赖**: 每个节点需3-5种前置材料，每种材料自身需2-3步合成
2. **新矿物解锁**: 每个阶段解锁1-2种新矿物，旧矿物用量不归零(始终有需求)
3. **机器串联**: 高级节点需要多台不同机器协作，强制玩家做自动化
4. **时间墙**: 某些材料故意设计为只能通过自动化产出(不能/d直接挖)，软性卡等待时间
5. **转生减负**: 转生后保留配方知识，卡脖子节点可通过token增益加速

## 五、自动化引擎设计

### 5.1 计划(P)数据结构

```typescript
interface Plan {
  id: string;
  playerId: string;
  machineId: string;      // 绑定的机器
  recipeId: string;        // 执行的配方
  priority: number;        // 1-99, 越小越优先
  mode: 'continuous' | 'limit' | 'pct';
  modeParam: number;       // limit=目标数量, pct=百分比
  status: 'active' | 'paused' | 'completed';
  createdAt: number;       // unix timestamp
}
```

### 5.2 配方竞争仲裁算法

```
输入: 玩家库存, 该玩家所有活跃计划(按priority ASC, createdAt ASC)
输出: 每项计划的材料分配方案

算法:
1. 深拷贝库存快照 → remainingStock
2. 遍历计划 P[i] (已按优先级排序):
   a. 计算配方单次所需材料 → recipeCost[j]
   b. 计算可执行次数: runs = min(remainingStock[j] / recipeCost[j]) 对所有j
   c. 如果 mode='limit': runs = min(runs, remaining_limit)
   d. 如果 mode='pct': runs按比例缩减
   e. 从 remainingStock 扣除 runs × recipeCost
   f. 产出写入临时产出表
3. 所有计划遍历完毕 → 产出合并打入库存
4. 如果本轮有任何计划执行(runs>0)，回到步骤2(材料释放后可让低优先级计划吃到)
   (连续两轮无执行则终止迭代，防止死循环)
```

### 5.3 离线结算流程

```
触发: 玩家发送任意指令
计算:
  1. T = min(now - lastTickTime, 24h)  // 离线时长上限
  2. tickCount = floor(T / tickInterval)  // tick间隔建议5-15分钟
  3. 循环 tickCount 次:
     a. 执行配方竞争仲裁算法(5.2)
     b. 更新库存
  4. 生成离线收益报告:
     - 材料变化(+X, -Y)
     - 完成/暂停的计划
     - /p limit达成的计划
  5. lastTickTime = now
返回: 离线收益报告(合并转发)
```

### 5.4 自动化机器类型

| 机器类型 | 功能 | 单tick产出倍率 | 解锁阶段 |
|----------|------|----------------|----------|
| 工作台 | 手动合成(/c的场所) | — | 石器 |
| 蒸汽引擎 | 解锁/p, 第一台自动化主机 | 1× | 蒸汽 |
| 组装机 | 电路类合成自动化 | 1× | LV |
| 线材机 | 线缆类合成自动化 | 1× | LV |
| 弯曲机 | 板材类合成自动化 | 1.2× | LV |
| 电解器 | 材料分解自动化 | 0.8× | MV |
| 化学反应釜 | 化工合成自动化 | 1× | MV |
| 洁净室 | 芯片级合成(必须) | 1× | HV |
| 蒸馏塔 | 多产物分离 | 1.5× | HV |
| 核反应堆 | 能源产出(提升所有机器倍率) | +50%全局 | EV |
| 组装线 | 并行合成(单tick可多次执行) | 3×并行 | IV |

## 六、Web UI设计(二期)

### 6.1 架构

```
[QQ群] ←→ [Bot进程] ←→ [SQLite]
                         ↓
                   [HTTP API服务] (内网端口, 如 :4200)
                         ↓
                   [Web前端] (SPA, 玩家浏览器访问)
```

### 6.2 API鉴权

- 玩家在QQ群发送`/i token`获取一次性绑定码
- 在Web页面输入绑定码+QQ号 → 生成JWT
- 后续请求携带JWT → 识别玩家身份
- Token有效期: 7天，可刷新

### 6.3 页面功能

| 页面 | 功能 |
|------|------|
| 仪表盘 | 材料库存总览、活跃计划数、阶段进度 |
| 库存管理 | 材料分类展示、数量、稀缺标记 |
| 基地布局 | 已放置机器可视化(2D网格或列表) |
| 计划管理 | 拖拽调整优先级、启停计划、新增计划 |
| 配方浏览器 | 配方图(材料→产物DAG)、合成路径规划 |
| 里程碑 | 当前阶段目标、已完成/未完成 |

### 6.4 技术选型建议

- 后端API: 与bot同进程，Express/Fastify，独立端口
- 前端: Vite + Vue/React，纯静态，Nginx或bot托管
- 无需数据库变更，HTTP API直接读写同一SQLite
- 写锁: bot操作和Web操作需互斥，SQLite WAL模式足够

## 七、数据模型概要

### 7.1 核心表

```sql
-- 玩家
players (id, qq, name, stage, prestige_count, prestige_tokens, created_at)

-- 材料库存
inventories (player_id, material_id, quantity)

-- 基地(已放置)
placements (id, player_id, item_id, placed_at)

-- 活跃计划
plans (id, player_id, machine_id, recipe_id, priority, mode, mode_param, status, created_at)

-- 配方
recipes (id, name, inputs JSON, outputs JSON, required_machine, stage_unlock, is_milestone)

-- 材料
materials (id, name, tier, category, diggable)

-- 机器定义
machines (id, name, tier, plan_slots, speed_multiplier)

-- 里程碑记录
milestones (player_id, milestone_key, achieved_at)
```

### 7.2 限速表

```sql
rate_limits (player_id, window_start, operation_count)
-- window_start: 8小时窗口起点
-- operation_count: 当前窗口已使用次数
-- 上限: 20次/窗口
```

## 八、开发分期建议

### 一期: MVP (核心循环验证)

- [ ] 数据模型 + SQLite持久化

- [ ] 材料池 + 基础配方表(石器+蒸汽阶段)

- [ ] 限速系统
- [ ] 合并转发消息打包

## 九、风险与注意事项

1. **QQ协议风险**: OneBot/NapCat有封号风险，建议用小号运行，不在主群测试
2. **材料膨胀**: 长期运行后材料数值可能溢出，使用BigInt或定期数值压缩(如1M→1K升级单位)
3. **配方平衡**: 初始配方若设计不当会导致某些材料永远冗余或永远短缺，需脚本模拟长期运行
4. **离线结算原子性**: 需确保结算中途崩溃不会导致材料复制或丢失，使用事务包裹
5. **合并转发稳定性**: 不同QQ客户端对合并转发展示效果有差异，需多端测试

首先，我觉得大体可以把和bot的交互分为/d (dig) /c (craft) /b (build) /p (plan)这四个操作指令和/i
  (idle_check)idle查询指令 ，意思就如括号里的描述一样
  作为避免过度玩bot，给用户限制为每8个小时最多操作bot若干次，接下来我将对指令做说明
  /d ，挖掘，即采集若干随机材料，获得的材料数量与放置增量内容相关，获得的材料等级和放置增量里程碑有关，是初始的获得资
  源的方式
  /c ，合成，把若干已有材料合成成工具/物品/机器，物品可能和放置增量里程碑有关(比如制作LV马达，才可以挖掘到LV的材料，这
  样的限制行为)，而机器则是和增量内容有关，做出来机器并布置则能通过一些方式得到自动合成/自动采集/采集效率增加/等一系列
  增益，或者处理流程
  /b , 放置，即把特定的工具/物品/机器，通过某种方式放置或者使用，放置下来的机器才能通过plan去定义行为，亦或者是放置下
  来的物品才能得到特定的材料
  /p , 计划，即自动化，放下来了机器或者一系列满足条件的内容后，才能通过/p
  指令指定进行特定的行为，比如说指定LV化学反应釜消耗若干材料制造若干材料，/p可附带参数，比如说优先级，或者用量百分比，
  或者得到数量终止，这是为了避免抢材料，抢同样配方材料是按优先级依次执行，有多少材料开始执行，获得多少材料停止，这样的
  设置操作，通过/p，就可以分多次的完成自动化和机器设置了

  以上是设想中的最基本的操作

  /i 则是展示出玩家拥有的资源，正在进行的自动化，/i也能附带参数，用于区分查询自己的信息，还是用于查询游戏配方，需求
